# Звіт про виконання лабораторної роботи №4  
## «Реляційна база даних у Node.js (PostgreSQL, SQL без ORM)»

**Тема проєкту:** розклад та результати спортивних змагань.  
**Стек:** Node.js, Express, EJS, PostgreSQL (Supabase), пакет `postgres`, без ORM.

Цей документ містить **детальний опис виконаних змін** та **умовний розподіл завдань між п’ятьма членами команди** (для звіту або презентації). Розподіл є **педагогічно зручним поділом відповідальності**; у реальному проєкті межі між ролями могли перетинатися.

---

## 1. Мета та вимоги, які було закрито

Лабораторна робота №4 передбачала:

1. Використання **реляційної СУБД** у середовищі Node.js.
2. **Проєктування схеми** (таблиці), **наповнення тестовими даними**.
3. **Заміна файлових заглушок** (JSON) на **реальний доступ через SQL** без ORM.
4. Для **хоча б однієї сутності** — повний **CRUD** (create, read, update, delete).
5. Операції **створення, оновлення та видалення** — у **транзакціях**.
6. **Бізнес-операція**, на якій видно **підтвердження транзакції** при успіху та **відкат** при помилці.
7. Архітектура репозиторіїв така, щоб **подальша заміна на ORM** (лаб. 5) вимагала мінімум змін у решті коду.

Усі перелічені пункти в проєкті реалізовано з урахуванням предметної області: **команди**, **ігри (розклад)**, **результати** та **журнал аудиту** для демонстрації транзакційної бізнес-операції.

## 2. Загальна архітектура після змін

### 2.1. Шари застосунку

| Шар | Призначення | Ключові елементи |
|-----|-------------|------------------|
| **Представлення** | HTML-сторінки (EJS) | Існуючі шаблони адмінки та розкладу; структура даних для в’ю збережена (`game`, `team1`, `team2`, `result`). |
| **Контролери** | HTTP-запити та відповіді | `schedule.controller.js`, `admin.controller.js` — переведені на **async/await** там, де потрібні асинхронні виклики до БД. |
| **Сервіс** | Бізнес-сценарії та збирання даних | `schedule.service.js` — агрегує команди, ігри та результати в об’єкт «розклад» для інтерфейсу. |
| **Репозиторії** | SQL-доступ, ізоляція від Express | `team.repository.js`, `game.repository.js`, `result.repository.js` — лише запити та мапінг полів. |
| **Підключення до БД** | Один клієнт PostgreSQL | `src/db/db.js` — читання `DATABASE_URL`, TLS для хмари, експорт `sql`. |

### 2.2. Чому без ORM

За умовами лабораторної **ORM не використовується**; запити формуються через **параметризовані шаблони** бібліотеки `postgres`, що знижує ризик SQL-ін’єкцій і зберігає явний контроль над SQL.

## 3. База даних: схема та дані

### 3.1. Файл `src/db/schema.sql`

Реалізовано такі таблиці в схемі `public` (типово для Supabase):

| Таблиця | Призначення |
|---------|-------------|
| **teams** | Довідник команд: `id` (TEXT PK), `name`, `city`, `logo`. |
| **games** | Розклад: `id`, `game_date`, `team1_id`, `team2_id`, `location`; зовнішні ключі на `teams`; обмеження, що команди в одній грі різні. |
| **game_results** | Поточний рахунок: `game_id` (PK, FK на `games` з `ON DELETE CASCADE`), `team1_score`, `team2_score`; перевірка не від’ємних голів. |
| **result_audit** | Журнал змін/фіксацій результату для **бізнес-операції** в одній транзакції з оновленням `game_results`. |

Скрипт **спочатку видаляє** таблиці (`DROP TABLE … CASCADE`), потім **створює** їх і **наповнює** даними, узгодженими з колишніми JSON-файлами (`teams`, `games`, частина `results`). У файлі є **інструкція**, що робити при помилці `relation … does not exist` (виконати скрипт у **тому самому** проєкті Supabase, що й `DATABASE_URL`).

### 3.2. Зв’язки

- Команда **бере участь у багатьох іграх** (логічно **1:N** через `team1_id` / `team2_id` у `games`).
- Гра **має нуль або один** запис результату в `game_results` (**1:0..1**).
- До однієї гри може бути **багато** записів у `result_audit` (**1:N**), що зручно для демонстрації історії введення результатів.

## 4. Підключення до PostgreSQL та конфігурація

### 4.1. `src/db/db.js`

- Підвантаження змінних з **`.env`** (через `dotenv`).
- Перевірка наявності **`DATABASE_URL`** з зрозумілим повідомленням про помилку.
- Для хмарних інстанцій (Supabase) увімкнено **`ssl: 'require'`**, якщо не встановлено `PGSSLMODE=disable` (для локального Postgres без TLS).

### 4.2. `.env` та `.env.example`

- **Секрети не потрапляють у репозиторій** (`.env` у `.gitignore`).
- У **`.env.example`** наведено **шаблон** для **Supabase Session pooler**: користувач вигляду `postgres.<project-ref>`, хост `aws-…pooler.supabase.com`, порт `5432`, з підказкою про transaction pooler / `prepare: false` за потреби.

### 4.3. `package.json`

- Додано залежності: **`postgres`**, **`dotenv`**.
- Скрипт **`npm run db:demo-tx`** — запуск демонстрації транзакцій.

### 4.4. `src/app.js`

- На початку додано **`require('dotenv').config()`**, щоб змінні середовища були доступні до завантаження маршрутів і репозиторіїв.

## 5. Репозиторії та вимоги лабораторної

### 5.1. Сутність «Гра» — повний CRUD (транзакційно)

Файл **`src/repositories/game.repository.js`**:

- **Read:** `getAll()`, `getById(id)` — вибірка з нормалізацією поля дати для сумісності з EJS (`game_date` → `date` у форматі `YYYY-MM-DD`).
- **Create:** `create(game)` — вставка в `games` у **`sql.begin(…)`**.
- **Update:** `update(id, data)` — оновлення рядка в транзакції.
- **Delete:** `remove(id)` — видалення в транзакції; за рахунок **CASCADE** зникають пов’язані рядки в `game_results` та `result_audit`.

Таким чином виконано вимогу: **усі чотири CRUD-операції** для однієї сутності та **транзакційність** для **create / update / delete**.

### 5.2. Команди

Файл **`src/repositories/team.repository.js`**:

- `getAll()`, `getById(id)` — читання з таблиці `teams` для форм адмінки та збирання розкладу.

### 5.3. Результати та бізнес-операція

Файл **`src/repositories/result.repository.js`**:

- **Read:** `getAll()`, `getByGameId(gameId)`.
- **`saveWithAudit(gameId, team1Score, team2Score)`** — **бізнес-операція** в **одній транзакції**:
  1. Перевірка, що гра існує.
  2. `INSERT … ON CONFLICT … DO UPDATE` у **`game_results`**.
  3. `INSERT` у **`result_audit`**.

Якщо будь-який крок падає, **вся транзакція відкочується** — відповідає вимозі про commit / rollback.

### 5.4. Демонстраційний скрипт

**`src/db/lab4-transaction-demo.js`** (запуск через **`npm run db:demo-tx`**):

- **Сценарій А:** навмисна помилка (порушення FK при вставці в `result_audit`) після зміни `game_results` — очікуваний **відкат**, дані не лишаються в неконсистентному стані.
- **Сценарій Б:** обидва кроки успішні — **підтвердження** транзакції.

Корисно для **звіту** та усного захисту.

## 6. Сервісний шар і контролери

### 6.1. `src/services/schedule.service.js`

- **`getFullSchedule`:** паралельно завантажує команди, ігри та результати (`Promise.all`), збирає об’єкти з `team1` / `team2` / `result` у форматі, який очікують існуючі шаблони.
- **`searchByTeam`**, **`getGameById`** — працюють поверх повного розкладу.
- **`createGame`**, **`updateGame`**, **`deleteGame`** — делегують у репозиторій ігор (асинхронно).
- **`saveResult`** — викликає **`saveWithAudit`**.
- **`getAllTeams`** — для форм створення/редагування гри.

Так зберігається **тонкий контролер** і **єдина точка бізнес-збирання даних** для представлень.

### 6.2. `src/controllers/admin.controller.js`

Усі дії, що звертаються до БД, оформлені як **`async`** з **`try/catch`** і відповідями `500` / `404` за потреби: панель, форми, створення, оновлення, видалення гри, форма та збереження результату.

### 6.3. `src/controllers/schedule.controller.js`

Логіка перегляду розкладу, картки гри та пошуку залишилася в тому ж стилі, з **`await`** до сервісу.

### 6.4. Маршрути

**`admin.routes.js`**, **`schedule.routes.js`** — без змін у структурі URL; оновлена лише поведінка хендлерів (асинхронність).

---

## 7. Що сталося з JSON-файлами

Файли в **`src/data/*.json`** перестали бути джерелом істини під час роботи застосунку: дані читаються та змінюються **лише в PostgreSQL**. JSON можна залишити як **еталон початкового наповнення** або для резервного копіювання; синхронізація з БД не виконується автоматично.

## 10. Як відтворити середовище (чеклист)

1. Створити проєкт у **Supabase**, виконати **`src/db/schema.sql`** у **SQL Editor**.
